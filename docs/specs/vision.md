# 项目愿景

> 动态文档。认识变化时更新，不追求一次写对。
>
> 本文档是项目宪法：开发决策不能超越它；冲突时先商议是否修改，再实施。
>
> 最后更新：2026-11-07

## 一句话

oh-my-fde（omfde）最终的产品形态是一个**企业内部的 FDE（Forward Deployed Engineer，前置交付工程师）项目管理平台**。以 Pi 为底座，参考 DSH（DeepSeek Harness）的平台化路径，一步一步演化，而不是重写或整体替换。

演化分三条线并行：**教程线**以文档为主线，**平台化线**以代码结构为主线，**FDE Code UI 线**以独立应用为主线。

价值理念：**极度精简 = 无限扩展**。平台本体极简、透明、白盒，把使用者从 Agent 配置里解放出来；每个 Agent Loop 环节都留扩展缝（可拦截、可改写、可增强，内核保持稳定、不做可拔插替换），靠渐进式增强承接无限业务，把更大的决策权留给 FDE、更大的业务想象空间留给甲方企业。

当前不做的事：**为了改而改**。核心代码已经由我们维护，但每次核心改动仍然要先证明现有扩展和配置不够。

## 产品形态

**最终形态：企业内部 FDE 项目管理平台。** coding agent 是平台的核心能力，但不是最终产品。平台内置 FDE 所需的工具链与插件扩展基建，把 FDE 项目初始阶段该做好的事务做好——让使用者以最快方式接入项目、聚焦业务逻辑实现，而不是把时间浪费在 Agent 配置上（基建透明、Agent 白盒化）。

平台要解决的不是“让一个人写代码更快”，而是让 FDE 在企业内部稳定地完成：

- 理解业务需求，并把它转成可运行的方案；
- 在真实代码库、数据源和企业系统中工作；
- 复用团队的知识、技能、工具和交付流程；
- 让权限、审计、评审和交接成为流程的一部分，而不是事后补丁。

平台至少包含四层：

| 层 | 当前状态 |
|---|---|
| 核心 agent | 基于 Pi，已跑通 |
| 工作方式 | prompt、skills、扩展、MCP，正在形成 |
| 团队协作 | Web UI 线已交付第一版（M3/M4：访问、工作区、归属、分享、交接、管理员、审计）；平台化线本体待固化 |
| 企业集成与治理 | Web UI 线已交付初步集成（M5：GitHub、CI、通知、保留策略）；平台化线本体待固化，治理未开始 |

近期平台化线本体仍只做前两层；后两层已由 Web UI 线（M3–M5）先行供料。后两层等“用好”阶段暴露真实需求后再设计。

## 首批用户

第一批 FDE 用户是以 Abel 为首的团队，规模 3~5 人。

这意味着当前阶段的优化目标是：

- 让团队里每个人都能复用同一套工作方式；
- 优先解决 3~5 人协作中的真实摩擦，而不是大型组织的治理问题；
- 团队通过 GitHub Issues 记录任务、bug 和阶段目标；新需求由决策者先发起讨论，再同步到 issue；
- 平台化能力以这个小团队的维护能力为上限，不按平台团队的规模铺开。

## 三条目标线

目标不是一条线性路径，而是三条并行、节奏不同的线：

```
线 1：教程线    理解 → 会用 → 用好                      以文档为主线
线 2：平台化线  骨架 → 核心能力 → 协作 → 企业集成 → 治理  以代码结构为主线
线 3：FDE Code UI 可用 → 对齐 DSH → 会话完整 → 团队可用    以独立应用为主线
```

- **教程线**回答“怎么理解、怎么用、怎么用好”，产物是文档、示例和验证记录。
- **平台化线**回答“代码和组织结构怎么长”，产物是仓库结构、包边界、扩展点和服务。
- **Web UI 线**回答“界面和交互怎么交付”，产物是一个独立可运行的 Web 应用。
- 三条线互相供料：教程线提供真实用法，平台化线固化结构，Web UI 线提供交互入口和真实反馈。
- 各线不必互相等待，但都不能先搭空架子；每条线的每一步都要有真实需求或可验证结果。
- 当前重心在平台化线“核心能力”层；教程线“会用”已完成、“用好”转入后台持续推进，不再作为门禁线。

### 线 1：教程线（以文档为主线）

#### 1. 理解（已完成基础）

- 读完核心架构：agent loop、session/transcript、projection、provider、扩展、工具、compaction、TUI。
- 用可运行脚本验证关键假设，而不是只读代码。
- 产物：`docs/explains/` 27 篇笔记 + 3 个验证脚本。

判定标准：能用自己的话解释一次请求从输入到落盘的完整路径，并能指出扩展点在哪。

#### 2. 会用（已完成）

- 用 Pi 完成真实的 FDE 工作，而不是跑测试样例。
- 掌握日常操作：会话、分支、压缩、扩展、MCP、模型切换、权限边界。
- 形成自己的使用习惯和配置，而不是照搬默认值。

判定标准：连续用它处理真实任务，遇到问题知道该看哪一层，而不是靠猜。

#### 3. 用好（转入后台，持续推进）

- 让它在团队协作、代码审查、长任务、多项目场景下稳定产出。
- 建立可复用的 prompt、skills、扩展和配置，把个人经验沉淀为团队工作方式。
- 明确它的边界：哪些事不该交给它，哪些环节必须人审。

判定标准：别人能按文档复现同样的工作流，效果不依赖某个人的临场技巧。

### 线 2：平台化线（以代码结构为主线）

按“先骨架、后能力、再协作与治理”的顺序推进：

1. **仓库骨架**（已完成第一版）：明确 apps / packages / extensions 的边界，建立最小可运行的平台入口。
2. **核心能力**（当前阶段，进行中）：把 FDE 高频工作固化为工具、skills、扩展和服务。
3. **协作层**：项目、任务、知识、评审和交接。
4. **企业集成**：代码托管、工单、知识库、CI/CD、部署、身份与权限。
5. **治理与规模化**：多团队、审计、成本、模型路由和升级策略；在首批 3~5 人团队之外再展开。

平台化线的约束：

- 优先扩展和配置，不轻易改核心。
- 每层只做已经被教程线验证过的能力，不预先设计。
- 保持 fork 历史可追溯；不再以持续 rebase 上游为目标。
- 核心代码可以修改，但必须走 vision → RAD → plan → 验证，不把“能改”当成“应该改”。
- 原“增强”不再是第四阶段，而是平台化线的总称。

### 线 3：FDE Code UI（以独立应用为主线）

按“先可用、再对齐、后完整”推进：

1. **可用界面**：在浏览器里新建会话、发送 prompt、流式查看文本/thinking/工具调用、中止。
2. **对齐 DSH**：布局和设计系统与 DSH 一致，样式用 Tailwind 实现，主题与共享控件成形。
3. **会话完整**：会话列表与恢复、模型切换、费用与 token、steering / follow-up。
4. **团队可用**：团队成员能各自用它完成日常工作，而不是只有作者能跑起来。

> 实际交付以里程碑 M1–M5 落地：M1 可用界面 + DSH 对齐起步、M2 会话完整、M3 团队可用、M4 协作与交接、M5 企业集成（M4/M5 向平台化线协作层/企业集成供料）。M1 之后以功能深度为主，DSH 视觉与设计系统的完整对齐是否单独排期见“未决问题”。

Web UI 线的约束：

- 独立应用：不依赖 `apps/omfde`，不作为 omfde 平台的子模块；先能单独启动、单独交付。
- 底座不变：通过 Pi 已有的 RPC 或 SDK 接缝接入，不为了 Web UI 重写 agent loop、session 或工具系统。
- 技术栈：遵循“前端技术栈”一节；Web UI 属于应用型界面，使用 TanStack Start。
- 本地优先，默认只监听回环地址；M3 起支持 3~5 人团队共用（可选 LAN 绑定 + 访问令牌认证），非回环监听必须启用认证。
- 不做多租户、组织架构与细粒度权限体系；M3/M4 已引入访问令牌登录与管理员/成员两级角色（RAD 判定为边界内、扩大部署与安全边界），但不做 SSO/LDAP/OAuth 与 RBAC；不做云端 IDE，不替代完整文件树与编辑器。
- 已通过组合式接入成为 omfde 默认界面（见决策记录“Web UI 作为 omfde 平台界面（组合式接入）”），代码保持独立、不合并；是否进一步做代码级并入仍未决。

#### 布局、设计系统与样式实现

| 层面 | 对齐内容 |
|---|---|
| 布局 | 三栏 AppFrame：左侧栏（会话/工作区）、中间会话、右侧可停靠面板；侧栏宽度范围、折叠与自动收起行为；窄屏抽屉；窗口 chrome 留白 |
| 设计系统 | 语义 token 分层（静态色阶 → 语义别名 → 组件变量）；light/dark/system 主题；字号与字体角色分离（正文、代码、终端）；圆角、阴影、焦点环、滚动条由主题统一拥有 |
| 样式系统 | Tailwind CSS 作为统一实现层：`--dsw-*` 语义 token 映射为 Tailwind theme 或工具类；共享控件先进 primitives 复用，不在功能包里复制；功能组件只消费语义 token 对应的工具类，不写字面色值、不写主题分支；全局样式表由主题层拥有 |

### 与 DSH 的关系

DSH 是参考对象，不是替换目标。三条线只借鉴它的组织方式和已验证做法。

#### 借鉴什么

- 插件与能力接缝的组织方式：Service Definition / Provider / Consumer。
- session 作为事实来源，以及 “Model-visible ⟺ logged” 不变量。
- 多端交付：CLI、Web、SDK、自动化协议共用同一套会话和事件。
- Web 客户端的布局骨架、token 分层和共享控件复用方式。
- 企业关注点：sandbox、credentials、approval、telemetry、workspace。
- 测试与发布纪律：快照回放、真实入口验证、构建产物与源码分离。

#### 不照搬什么

- 379 个包、30 条 workflow、per-file 100% 覆盖这类大规模流程。
- 用全插件架构重写 Pi；我们保持 Pi 为底座，优先扩展。
- DSH 的 pre-stable 契约和 breaking changes 节奏。
- DSH 样式规范中“只用 CSS Modules、禁止 Tailwind”的限制；我们用 Tailwind 实现同一套设计系统。
- 为对齐视觉而重写 Pi 的会话、工具或 TUI。

## 前端技术栈

前端开发统一使用一套栈，避免每个应用各起一套：

| 场景 | 栈 |
|---|---|
| 应用型界面（FDE Code UI、平台控制台等） | React + TanStack Start + Tailwind CSS + Vite |
| 内容型站点（文档、博客、官网） | React + Astro + Tailwind CSS + Vite |

- **分界按交互形态，不按项目大小**：需要长会话、实时状态和复杂交互的用 TanStack Start；以阅读和展示为主的用 Astro。
- **React 是统一组件模型**：两种栈都用 React，组件、hooks 和设计 token 可以互相迁移。
- **Tailwind CSS 是统一样式层**：设计系统仍由主题层提供 token，Tailwind 负责消费。
- **Vite 是共同构建基础**：TanStack Start 和 Astro 都基于 Vite，构建、开发服务器和环境变量约定保持一致。
- 具体版本在 plan 中锁定，不在本文档中固定。

## 已确认的系统认识

这些是后续决策的地基，来自代码阅读和实际运行：

1. transcript 是追加写的 JSONL，历史不原地修改。
2. 每条消息在 `message_end` 落盘。
3. 请求上下文由 session projection 重建，不是直接复用内存数组。
4. `context_edit` 是追加式 amend，原始记录保留。
5. compaction 是检查点，不是删除；`systemMessage` 快照保证压缩后 prompt 不丢。
6. `tool_call` 是所有工具调用的统一接缝，包括 codemode / MCP 的嵌套调用。
7. 嵌套调用带 `parentToolCallId`，返回 `{ block: true }` 可以阻止执行。
8. 扩展能在不改内核的前提下完成拦截、改写和工具编排。

第 6、7、8 条意味着：**权限、审计、门禁这类需求，第一选择是扩展，不是改内核。**

## 决策记录

### 2026-11-06：目标顺序调整为 理解 → 会用 → 用好 → 增强

原因：读完并验证 Pi 后，确认现有扩展机制已覆盖最初设想的改造点。在尚未用熟之前修改内核，收益不确定，且会失去与上游同步的能力。

影响：暂缓“权限扩展”等实现工作，先进入“会用”阶段。何时进入“增强”，由真实使用中的缺口触发，而不是由计划表触发。

### 2026-11-06：AGENTS.md 改为 fork 专属规则

原因：上游 `AGENTS.md` 仍包含 `apps/p2`、`packages/chord`、`packages/durable` 的规则，这些目录在本 fork 中已删除；同时上游规则没有区分“理解/会用”和“增强”阶段。

影响：删除 Chord v2 章节和 p2/durable 相关命令，新增“当前状态”“环境与测试模型”“分支、Git 与上游”“文档”四节；明确当前阶段优先使用配置和扩展，核心改动必须先在本文档记录决定。中文译本 `AGENTS.zh-CN.md` 同步更新。

### 2026-11-06：产品形态澄清为企业内部 FDE 平台

原因：此前把目标描述为“个人和团队都能长期使用的 coding agent”，容易把最终产品误解为一个通用编码工具。实际定位是企业内部的 FDE 平台，coding agent 只是平台的核心能力。

影响：一句话和产品形态改为“以 Pi 为底座，先做透 coding agent，再逐步补齐团队协作、企业集成与治理”。近期仍只做核心 agent 和工作方式两层；平台化能力等真实需求出现后再建设。

### 2026-11-06：演化路径参考 DSH，但在 Pi 上逐步平台化

### 2026-11-07：产品定位澄清——FDE 项目管理平台与「极度精简 = 无限扩展」

原因：决策者澄清 omfde 的定位与价值理念：omfde 是一个 **FDE 项目管理平台**，内置 FDE 所需的工具链与插件扩展基建；定位是把 FDE 项目初始阶段该做好的事务做好，不让使用者把时间浪费在 Agent 配置上（基建透明、Agent 白盒化），以最快方式接入项目、聚焦业务逻辑实现。价值理念是**「极度精简 = 无限扩展」**：架构上做渐进式增强，让每一个 Agent Loop 环节都可扩展，把更大的决策权限留给 FDE、更大的业务想象空间留给甲方企业。

影响：本条是对既有目标的澄清与收敛，不改变当前阶段（平台化线核心能力）与三条目标线，也不新增边界。「极度精简 = 无限扩展」把既有的「不为改而改」「优先扩展与配置」「每层由真实缺口触发、不预先设计」收敛为一条命名理念；「基建透明、Agent 白盒化」与原则一（稳定透明底座）及 agent-visibility 观测面一致；「决策权留给 FDE」与原则三（人主 Agent 辅）一致，并明确「业务想象空间留给甲方企业」——平台不自建业务逻辑，靠极简可扩展底座承接各甲方项目。「可扩展的每一个 Agent Loop 环节」按**扩展缝**理解（决策者已确认）：经既有 `tool_call`/扩展/事件缝做到可拦截、可改写、可增强即已足够，**不需要把内核做成可拔插替换**；内核强调**稳定**、不采全插件化，与「长壳不长核」一致，「不全插件化」这条边界不放宽。产品身份补「项目管理」维度，与未决问题「平台化线的下一刀：项目/知识/权限/审计」相关，但不在此预定实现顺序。

### 2026-11-07：澄清「极度精简」不等于粗放，极致 UI/UX 体验为既定目标

原因：决策者澄清「极度精简 = 无限扩展」的边界：精简指不引入重量级子系统与无谓复杂度，绝不是在 UI/UX 打磨上粗放；对极致用户体验的追求是既定目标，不因精简定位而放弃。触发点：对照 opencode app 前端梳理可借鉴项时，部分交互体验增强被误判为「与极简定位冲突故推迟」，需纠正该口径。

影响：本条是对既有理念「极度精简 = 无限扩展」（见 2026-11-07「产品定位澄清」条）的澄清与收敛，不改变当前阶段（平台化线核心能力）、三条目标线与边界，也不新增目标。明确三点：①「精简」的对象是重量级子系统与无谓复杂度，不是交互细节、可访问性与视觉打磨；②追求极致 UI/UX 体验是既定目标，相关增强按真实缺口与 vision → RAD → plan 纪律排序推进，不以「与极简冲突」为由预先排除；③是否引入某项重量级子系统，仍按「不为改而改、优先扩展与配置、每层由真实缺口触发」逐案判定。线3（FDE Code UI）的「对齐 DSH」与「布局、设计系统与样式实现」是本原则的既有落点。
